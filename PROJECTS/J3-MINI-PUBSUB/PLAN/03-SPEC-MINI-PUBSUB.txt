     aur listener baad mein unsubscribe kar sake.

----------------------------------------------------------------

  object, object method syntax, Map, Set, class, ya object payload use nahi
  karna. Sirf already-learned functions, callbacks, closures, arrays, and

      const bus = createPubSub();
      const unsubscribe = bus("subscribe", "saved", listener);
      bus("publish", "saved", "file-1");

----------------------------------------------------------------
STORY (real problem)
----------------------------------------------------------------
  Real applications mein ek action ke baad multiple parts ko pata chalna
  padta hai: save complete hua, ya koi channel change hua. Har part ko
  doosre part ko directly call karne se coupling badhti hai.

  J3 ka bus ek simple boundary dega:
      subscribe → publish → listeners receive → unsubscribe

----------------------------------------------------------------
FUNCTION CONTRACT
----------------------------------------------------------------
  Factory:
      createPubSub()

      Ek dispatcher function return karo. Us dispatcher ko teen arguments
      mil sakte hain: action, eventName, value.

  Subscribe action:
      bus("subscribe", eventName, listener)

      Valid call par ek unsubscribe function return karo. Us function ko
      call karne ke baad wahi listener us event ke liye dobara nahi chalega.

  Publish action:
      bus("publish", eventName, payload)

      Event ke current listeners ko registration order mein payload do.
      Return value = kitne listeners ko notify kiya gaya.

  Safe invalid behaviour:
      Invalid action, event name, ya listener par crash nahi hona.
      Invalid subscribe ek safe no-op unsubscribe de sakta hai.
      Invalid/no-subscriber publish ka result 0 ho sakta hai.

----------------------------------------------------------------
RULES (code-free)
----------------------------------------------------------------
  R1  Event name non-empty string hona chahiye.

  R2  Listener function hona chahiye.

  R3  Ek event ke multiple listeners ho sakte hain.

  R4  Listeners registration order mein call honge.

  R5  Alag event names ek doosre ke listeners ko trigger nahi karenge.

  R6  Unsubscribe sirf apna listener remove karega; doosre listeners safe
      rahenge. Same unsubscribe ko dobara call karna safe hona chahiye.

  R7  Same event par same listener ko do baar subscribe karne par duplicate
      notification nahi honi chahiye.

  R8  Kisi event ka listener na ho to publish crash nahi karega aur `0`
      return karega.

  R9  Payload ko bus change nahi karega; listener ko wahi primitive payload
      milega.

  R10 Do alag `createPubSub()` calls ke buses isolated honge.

  R11 Internal state closure ke andar private rahega. No global list, no
      object syntax, no Map, no Set, no class, no UI, no network, no async.

----------------------------------------------------------------
ACCEPTANCE PROOF — 8 CHECKS
----------------------------------------------------------------
  1. One listener receives one published primitive payload.
  2. Multiple listeners receive the same event in registration order.
  3. Different event names remain isolated.
  4. The returned unsubscribe function removes only its listener.
  5. Repeated unsubscribe and publishing with no listeners do not crash.
  6. Duplicate subscription does not deliver the same listener twice.
  7. `publish` returns the number of notified listeners.
  8. Two bus instances remain independent and the payload passes unchanged.
